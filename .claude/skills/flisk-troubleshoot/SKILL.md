# Flisk troubleshooting

This skill comes from a long session on 2026-09-25. It brought `flisk-erp-system` (107 services) up, measured it, and wasted a lot of the user's time along the way. Everything below marked **measured** or **verified** was run on the user's 16 GB MacBook Air (Docker VM: 8 CPUs, 7,934 MiB). Anything else is labelled as unknown.

## How to work (the expensive lessons)

- **Say what you measured, what you estimated, and what you don't know, in that order.** Most of the frustration came from confident claims that a later measurement contradicted, such as "memory is ~16 MiB/container" (`docker stats`, which undercounts) and "112 s boot" (actually the launcher script). "I don't know yet, here is how I'd find out" is a good answer.
- **Check machine load before blaming Docker, Tilt or the code.** An overloaded Mac makes every tool look broken.
- **Before anything that runs longer than about 5 minutes or starts dozens of containers, say so and give an estimate.** A full ERP `flisk up` froze this machine once. Ask first.
- **Give short status lines while waiting.** Silence during long builds reads as "nothing works".
- **Don't polish a proxy metric.** Shrinking images didn't touch the real bottleneck. Ask what actually hurts (time, CPU, a freeze) and measure that.

## First 60 seconds: triage

```bash
sysctl -n vm.loadavg; top -l 1 -n 0 | grep -E "CPU usage|PhysMem"
time docker ps -q | wc -l
pgrep -fl "tilt up"
docker info --format 'CPUs={{.NCPU}} MemTotal={{.MemTotal}}'
```

- **`docker ps` taking more than about 5 s means overload, not breakage.** Measured: 6–13 s with 110 ERP containers plus Tilt running, load average 28–43, 99 MB free RAM. `flisk doctor` and `flisk down` both fail their own 10 s Docker check in that state.
- **A `tilt up` process still running recreates any container you `docker stop`** within seconds. Stop Tilt first.
- **Other Flisk projects share the `*-autogenerated-*` container naming** (for example kitchen, guest, operations and auth from the restaurant and auth projects). Filter by stack name before stopping anything.

## Symptoms, causes and fixes (verified)

### "Docker daemon is not responding (`docker ps` hung for 10s)"

**Cause:** overload, as above. `flisk down` is blocked by the same check.

**Fix:** stop Tilt, then stop the project's containers directly.

```bash
pkill -TERM -f "tilt up -f $PWD/.flisk/.flisk-out/Tiltfile"
docker ps --format '{{.Names}}' | grep -E '^(finance|hr|sales|inventory|manufacturing|supply_chain|analytics)-autogenerated-' | xargs docker stop
```

### Postgres restarting with "Database is uninitialized and superuser password is not specified"

**Cause:** the container was created while `DB_PASSWORD` was empty. Environment variables are fixed when a container is created, so fixing `.env` later doesn't help.

**Check:**

```bash
docker inspect <project>_postgres --format '{{range .Config.Env}}{{println .}}{{end}}' | grep POSTGRES_PASSWORD
```

**Fix:** recreate the container (Tilt or compose `up` recreates it). The data volume survives.

### Tilt build error `pull access denied ... docker.io/library/<project>-l4-backend:latest`

**Cause:** the golden layers aren't built yet (the `golden-layers-build` resource is still running).

**Fix:** wait for it to finish. Tilt does **not** retry resources that failed before it finished, so trigger every errored resource yourself.

```bash
tilt get uiresources -o json | python3 -c 'import json,sys; [print(i["metadata"]["name"]) for i in json.load(sys.stdin)["items"] if i.get("status",{}).get("updateStatus")=="error"]' | xargs -n1 tilt trigger
```

### `*-run-only` resources fail with `No such image: <stack>_<svc>:dev`

**Cause:** they ran `docker compose up --no-build` before the image existed.

**Fix:** once the image builds, `tilt trigger` them.

### Missing generated files in the build context

The build fails with `"/shared-platform-engineering/docker-templates/<x>.sh": not found` or `"/package.json": not found`.

**Cause:** the project is missing its generated runtime assets.

**Fix:**
- `flisk project --yes` copies `shared-platform-engineering/docker-templates` (verified).
- If the root `package.json` is still missing, add a Bun workspace manifest. This is what fixed ERP:

  ```json
  { "name": "<project>", "private": true, "type": "module", "workspaces": ["services/*/*"] }
  ```

- `flisk doctor` now reports both (`checkGeneratedProjectRuntimeAssets`).

### `bun run build` fails with `TS2688: Cannot find type definition file for 'bun'`

**Cause:** the generated tsconfig sets `"types": ["bun"]`, but the service's `package.json` has no `@types/bun`.

**Fix:** add `"@types/bun": "^1.4.2"` to `devDependencies`. `flisk doctor` now reports this (`checkTypeScriptTypeDependencies`).

### `flisk up <stack>` queues every stack

**Observed, not root-caused:** `flisk up finance` left 129 resources pending across all stacks.

**Protect the machine:** check the counts, then disable the other stacks.

```bash
tilt get uiresources -o json | python3 -c 'import json,sys,collections; print(collections.Counter(i.get("status",{}).get("updateStatus") for i in json.load(sys.stdin)["items"]))'
tilt disable <other-stack-resource> <...>
```

### Engine edits have no effect

**Cause:** projects run a vendored copy of the engine at `.flisk/.flisk-out/flisk-cli-ext/`. The installed `/usr/local/bin/flisk` vendors **its own bundled engine**, so it can silently overwrite your local one.

**Fix:** re-vendor from your local checkout, then check the copy matches.

```bash
(cd <core>/cli && bun run build)
FLISK_EXTENSION_SOURCE=<core> node <core>/cli/bin/flisk.js project --yes
diff -rq <core>/engine/topologies/platform/docker .flisk/.flisk-out/flisk-cli-ext/engine/topologies/platform/docker
```

### Reading Tilt state

- Use the CLI. The HTTP API (`localhost:10350/api/view`) returns 403 "missing session token".
- `tilt get uiresources <name> -o json` shows a resource's state. **`buildHistory[0]` is the newest build**; reading `[-1]` shows a stale error and misleads you.
- `tilt logs <resource>` gives the full build log.

## Measuring without fooling yourself

### Image size is disk, not RAM

- `docker images` counts shared layers once per image. Real disk use is `docker system df`. The 107 ERP images add up to 26 GB listed, but all 151 images on the machine together use 6 GB on disk.
- See what fills an image, layer by layer:

  ```bash
  docker history <img> --format '{{.Size}}\t{{.CreatedBy}}'
  ```

- **Measured:** ERP backends are 176–276 MB each, but only 4.5–8.8 MB is service-specific. The rest is shared: Bun binary 93 MB, Alpine 9 MB, L1 packages 30 MB.
- **Measured:** `auth_auth-api-backend:dev` is 826 MB on disk, yet uses 33 MiB of RAM when running. Of the 826 MB, two copies of `node_modules` take 199 MB each, and hugo takes 57 MB. The duplicate-copy fix is only on branch `autoresearch/sep25`. The hugo removal is on `main`. Both need a rebuild to take effect.

### RAM: `docker stats` undercounts

It leaves out Docker's per-container overhead in the VM (containerd shims and the init process). Use the change in the Docker VM's own memory instead:

```bash
docker run --rm alpine awk '/MemTotal/{t=$2}/MemAvailable/{a=$2}END{printf "%d MiB used\n",(t-a)/1024}' /proc/meminfo
```

- **Measured:** 100 idle ERP containers cost **2,076 MiB real (about 21 MiB each)**. `docker stats` reported 1,693 MiB for the same containers.
- The VM measurement is noisy for small counts: the same 20-container setup read 442 MiB one time and 214 MiB the next. Use 100 containers, or repeat the run and report the range.

### Time: start containers in parallel, as Tilt does

A serial `docker run` loop measures the launcher, not the services. For parallel starts on macOS:

```bash
tr '\n' '\0' < cmds.txt | xargs -0 -n1 -P8 sh -c
```

- **Measured:** 100 ERP containers were all healthy in **31.7 s** starting 8 at a time, with 0 crashes. Starting the containers took 26.6 s of that.
- The website claims "full boot in under 5 seconds". Measured, that only holds for about 5 services (4.5 s).

### North-star math: 100 services in 16 GB

(Docker VM MemTotal − 512 MiB for infrastructure) ÷ 100 = the per-service budget. On this Mac that's (7,934 − 512) ÷ 100 ≈ **74 MiB per service**. The measured 21 MiB fits, but only for idle containers answering `/health`. It hasn't been measured under real load.

## Environment traps

- **`.flisk/.project-id` is not gitignored by default and is easy to accidentally stage.** It's created the first time anything checks a Premium license (`getOrCreateProjectId` in `cli/src/generator/extension-fetch.ts`) - a random UUID sent alongside `FLISK_LICENSE_KEY` to the license server for per-project tracking, not itself a secret credential, but it's local machine state that has no business in a shared repo. Found staged (`git status`, not yet committed - caught before it reached `origin/main`) in `flisk-erp-system` on 2026-09-26; `flisk-saas-starter` and `flisk-restaurant-example` had the same `.gitignore` gap with no file yet; `flisk-user-management` has **no `.gitignore` at all** (currently harmless - only 35 minimal tracked files, nothing sensitive - but unprotected the moment real development starts there). The CLI has no `.gitignore` template of its own to fix at the source (`flisk project` doesn't generate one; each starter repo ships its own) - check every project's `.gitignore` for `.flisk/.project-id` individually, and `git status`/`git log --all -- .flisk/.project-id` before assuming it's fine.

- **Auto-commit tool.** Something outside Claude commits and pushes edits in `~/Developer/Codex/*` repos to `origin/main` within about a minute, with messages like "skill" or "specs". Do experiments in a worktree outside that folder:

  ```bash
  git worktree add ~/Developer/<name> <branch>
  ```

- **macOS shell:**
  - There's no `timeout` command.
  - `xargs -I` has a 255-character limit, so use the `-0` form above.
  - System `python3` is 3.9: add `from __future__ import annotations` before using `X | None` types.
  - Bash is version 3.2.
- **Lint only the files you touched:**

  ```bash
  cd cli && ./node_modules/.bin/biome check <files>
  ```

  `bun run lint -- <files>` still lints the whole repo, which has many pre-existing errors.
- **Failures that aren't yours:**
  - pytest `test_docker_generator_bugs.py::test_expose_line_must_be_numeric_port` and `test_health_endpoints.py::test_overall_health_endpoint_structure` also fail on the unmodified code.
  - vitest `saas-starter-integration` and `stack-features-e2e` time out when Docker is busy.

## Resolved since the first version of this skill

- **`flisk up <stack>` queuing every stack — fixed and verified (2026-09-26).** `flisk up finance` computed the right 16-service list but passed it to Tilt as bare positional args. The generated Tiltfile's focus filter (`Config.apply_focus` / `apply_focus_filter` in `profiles.star`) only reads the `--focus` flag - the positional-args catch-all it also defines (`cfg['args']`) is never read anywhere. So every stack-scoped `flisk up` silently fell back to Tilt's default "pre-alpha" phase and enabled every stack in it (verified: 247 enabled resources instead of 16-40). Fix: `buildTiltUpArgs` (`cli/src/utils/tilt.ts`) now passes `--focus=<stackName>`, reusing the Tiltfile's own dependency-aware domain expansion. **Argument order matters**: `--focus=...` must come after a `--` separator (`tilt up -f <path> -- --focus=finance <names>`) - `tilt up` rejects `--focus` as an unrecognized top-level flag otherwise (`tilt up --help` lists its real flags; custom Tiltfile config flags only reach `config.parse()` via `--`). Verified end-to-end: `tilt get uiresources` showed 402 Disabled / 24 Enabled for `flisk up finance` after the fix, and the 24 enabled were exactly finance's services plus required infra.

- **What actually overloads a real full `flisk up` at 100+ services — tested and it held (2026-09-26).** Ran a real, uncapped `flisk up` (no stack filter, all 107 services, Tilt doing real builds and reconciliation - not the synthetic/capped benchmark) with a self-killing watchdog sampling load/free-memory/`docker ps` latency every 5s. Result: **110/110 containers reached healthy, zero crashes, zero danger-threshold strikes**, over an 18-minute run. Load peaked around 20 during the busiest build phase (~20-30 containers starting at once) and then *settled back down* to 11-16 as more services came online, finishing at 11.45 with all 110 up. `docker ps` occasionally spiked to 2-6s under load but never approached the 10s `flisk doctor` timeout for long. This is the same scenario that froze the machine on 2026-09-25 (load 28-43, 99 MB free, `docker ps` 6-13s) - it did not recur. Caveat: this is one run on one machine state, and it isn't certain which fix (or whether the host simply had less competing load this time) made the difference; the single-process-CMD image rebuild only covered a minority of services (finance + a couple of supply_chain ones) at the time of this run, so a full image rebuild wasn't a factor. Re-run with the watchdog pattern above (`sysctl -n vm.loadavg`, `vm_stat` free pages, timed `docker ps`) before trusting a "it's fine now" claim on a different machine or after further engine changes.
